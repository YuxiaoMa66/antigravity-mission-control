# v0.5.0：可信的任务状态，经真实 AGY CLI 验证

本稳定版把 v0.4.2 各候选版本中的 `cli.py` 模块拆分带到 `@latest`，并修复了只有在针对真实 AGY CLI 测试时才暴露的问题。路由与 Skill 工作流不变，运行时路由仍是 v0.3.0 的 Flash 优先设计。npm 版本号：`0.5.0`。

**可信的结果判定**

- 失败的 AGY 运行不会再被报告为成功。非零退出码一律判为失败，部分响应只作为证据保留。没有响应的 `ERROR` 结果判为失败，`SUCCESS`、`ERROR` 之外的任何状态也判为失败。`done_with_warnings` 只覆盖两种情况：正常退出且 `ERROR` 结果仍带有响应，以及 `SUCCESS` 但没有响应。
- AGY 自身的 print timeout 会中断这一轮，却仍报告 `SUCCESS` 且响应为空。这种情况现在判为失败，退出码 124。
- AGY 1.2 把结果嵌套在 `result` 之下。Mission Control 此前只从顶层读取 `status` 和 `conversation_id`，所以嵌套的 `ERROR` 可能被放过，任何任务都记录不到会话 id，`agy-mc continue` 在 AGY 1.2 上也就无法使用。现在两种结构都能读取。0.5.0 之前记录的任务仍然没有会话 id，无法续接。
- 失败的后台 worker 不会再因为 AGY stderr 中的文字被改标为 `done_with_warnings`。
- 使用 `--json-schema` 时，如果答案不是单个 JSON 文档，会报告为 `done_with_warnings`，而不是干净的成功。AGY 并不总是遵守 schema。
- AGY 并不强制 `plan` 模式只读：真实运行中，plan worker 曾创建文件。改动了 Git 工作区的 `plan` 运行现在会以退出码 5 失败，并列出改动的路径。
- print timeout 的错误会指出 AGY 卡在哪一步（`stuck_step`），无需重跑即可诊断卡住的运行。

**worker 专注于任务**

- Mission Control 不再给每个提示词都附加工作区说明。只有工作区已有改动时才会发送，内容只列出这些路径，也不会再把 Mission Control 私有证据的位置告诉 worker。真实运行中，拿到该位置的 worker 有时会把整轮都花在读取任务文件上，而不是完成任务，直到超时。

**没有竞态的任务生命周期**

- 启动、取消、worker 完成和状态刷新都在短时的单任务锁内更新任务。启动过程中到达的取消不会再被覆盖为 `running`。
- 启动进程退出后，任务不会再卡在 `starting`。取消命令本身被中断时，任务也不会再卡在 `canceling`：`status`、`result` 和 `wait` 会把它收敛到同一个终态。

**更安全的默认行为**

- 宽泛目录不能再作为工作区：home 目录的上级（例如 `/Users`）以及系统临时目录根。
- `agy-mc skill uninstall` 会拒绝不是由它安装的目录，除非传入 `--force`。npm `uninstall` 会在做任何修改前检查所有目标。

**经真实 AGY CLI 验证**

- `scripts/real_agy_check.py` 是可复用的验收套件，通过 Mission Control 驱动本机安装的 `agy`。共 19 个场景：离线守卫、前台与后台运行、`continue`、取消、worker 被杀、取消中断、wait 超时、并行只读任务、`--json-schema`、print timeout、`plan` 模式下的写入、编辑锁与工作区证据。发布流程现在要求全部通过。
- CI 在 macOS 上运行生命周期测试，并在声明的最低版本 Node 18 和 Node 20 上测试 npm 包，包括安装打包后的 tarball。

安装或更新：`npx antigravity-mission-control@latest install`，或 `python3 -m pip install "git+https://github.com/YuxiaoMa66/antigravity-mission-control.git@v0.5.0"`。验证：64 个 Python 测试、13 个 npm 测试，以及针对 AGY 1.2.8、使用 `gemini-3.8-flash-high` 的 19 个真实 AGY 场景全部通过。

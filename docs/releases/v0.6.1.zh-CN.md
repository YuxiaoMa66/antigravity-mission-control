# v0.6.1：诊断 AGY 启动缓慢

本稳定版新增了一项诊断，针对我们在 AGY 1.2.14 上实测到的启动缓慢问题。任务行为、路由与 Skill 工作流不变。npm 版本：`0.6.1`。

**AGY 为什么会启动很慢**

- headless 的 `agy -p` 会等所有已配置的 MCP 服务器连接成功或超时（每个 30 秒）之后，才发出第一个真正的模型请求。一个挂起的 MCP 服务器会让一次简单调用从 5 秒变成 67 秒。在 headless 模式下，`agy mcp disable` 不能避免这段等待。

**如何诊断**

- `agy-mc doctor` 新增 `agy-mcp` 检查，列出已启用的 AGY MCP 服务器，并警告每个服务器都可能让每个任务最多多等 30 秒。它不会调用模型。
- `agy-mc doctor --probe-latency` 会用最新的 Gemini Flash High 模型实测一次最小调用，报告耗时；超过 20 秒时警告，并把已启用的 MCP 服务器列为嫌疑。它会消耗少量额度。警告不会改变 doctor 的退出码。
- `scripts/real_agy_check.py` 现在给锁释放后的那一轮调用留出 120 秒，冷启动不会再让该场景失败。

**经真实 AGY CLI 验证**

- `scripts/real_agy_check.py`：针对 AGY 1.2.14、使用 `gemini-3.8-flash-high`，连续两次完整运行，每次都是 19/19。AGY 1.2.9 到 1.2.14 之间，唯一影响 Mission Control 的改动是 `--json-schema` 现在会拒绝根类型不是对象的 schema；Mission Control 原样传递 schema 文件。

安装或更新：`npx antigravity-mission-control@latest install`，或 `python3 -m pip install "git+https://github.com/YuxiaoMa66/antigravity-mission-control.git@v0.6.1"`。验证：112 个 Python 测试、13 个 npm 测试，以及连续两次完整运行中各 19/19 的真实 AGY 场景。
